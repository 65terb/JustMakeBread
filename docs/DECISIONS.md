## 2026-08-06 — 카메라 시점 전제 철회 (과거 전제 철회 기록)

- 선택지:
  1. 기존 고정 직교 쿼터뷰 유지
  2. 다른 특정 시점으로 즉시 확정

- 결정: 고정 직교 쿼터뷰와 2.5D 전제를 철회한다. 현재 카메라는 기술 검증용 임시 구현으로 취급하며 최종 방식은 플레이테스트 후 결정한다.

- 검증 방법: 블록 운반과 토큰 생산이 구현된 프로토타입에서 플레이어·대상 블록·주요 적체가 지속적으로 읽히는지 비교한다.
- 재검토 조건: 토큰 5개 연속 흡수와 기본 생산 사슬이 구현된 후 카메라 비교 테스트를 실시한다.

## 2026-08-06 — 임시 카메라 공동 프레이밍 검증 (이전 결정, 철회)

- 날짜: 2026-08-06
- 문제: 최종 시점을 확정하지 않은 상태에서 플레이어와 현재 이동 블록을 화면 안에 함께 유지하는 임시 카메라 기준을 어떻게 검증할 것인가?
- 선택지:
  1. 플레이어만 기준으로 카메라를 추적한다.
  2. 블록이 화면 밖으로 나가면 별도 대상 표시를 추가한다.
  3. 임시 카메라가 플레이어와 현재 블록을 함께 프레이밍하고 실제 투영으로 검증한다.
- 결정: 당시 첫 상호작용 검증을 위해 플레이어와 현재 블록을 함께 프레이밍했다. 이 결정은 아래의 직접 운반·플레이어 중심 임시 카메라 결정으로 대체되었으며, 최종 카메라·투영·시점 방식을 확정한 기록은 아니다.
- 근거: 유일한 블록을 운반하고 배치하는 단계에서는 플레이어와 대상 블록의 위치 관계를 동시에 읽을 수 있어야 하며, 별도 게임 기능을 추가하지 않고 카메라 프레임 계산으로 검증할 수 있다.
- 검증 방법: `src/camera.test.ts`에서 반대편 유효 모서리의 플레이어 `(5.5, 3.5)`와 블록 `(-5, -3)`을 실제 `THREE.Vector3.project(camera)`로 투영하고, 16:9와 800×600 화면비 모두에서 두 대상의 NDC x·y·z가 `-1..1` 범위인지 단언한다.
- 재검토 조건: 토큰 5개 연속 흡수와 기본 생산 사슬이 구현된 후 다른 투영·시점 후보와 비교 플레이테스트를 진행하거나, 실제 투영 테스트가 실패하는 카메라 결함이 발견될 때

## 2026-08-06 — 단계 2 이후 카메라 후보 유지

- 날짜: 2026-08-06
- 문제: 최소 생산 루프가 구현된 뒤에도 최종 카메라 시점을 지금 확정할 것인가?
- 선택지:
  1. 고도 고정·좌우 회전 카메라를 채택한다.
  2. 자유 3인칭 카메라를 채택한다.
  3. 자유 1인칭 카메라를 채택한다.
- 결정: 세 후보를 모두 유지하고, 현재 플레이어 중심 고정 추적 카메라는 기술 검증용 임시 구현으로 계속 사용한다. 최소 생산 루프가 안정된 뒤 플레이어 이동, 재료 운반·투입, 토큰 적체 판독, 출력 가독성을 기준으로 비교한다. 이번 작업에서는 새 카메라 조작이나 최종 시점 확정을 하지 않는다.
- 근거: 직접 재료 운반에서는 대상 설비나 주변 토큰의 변화가 카메라 중심과 배율을 바꾸면 이동·거리·투입 판단이 흔들릴 수 있지만, 생산 루프만으로 최종 시점의 조작감 우위를 판단할 증거는 부족하다.
- 검증 방법: 단계 2 최소 생산 루프에서 현재 임시 플레이어 중심 추적의 생산 상태 가독성을 확인하고, 이후 세 후보를 동일한 생산 시나리오에서 비교 플레이테스트한다.
- 재검토 조건: 단계 2 플레이테스트에서 특정 후보가 이동·운반·투입·병목 판독을 일관되게 방해하거나, 동일 조건 비교 결과가 충분히 축적될 때

## 2026-08-06 — 직접 재료 운반과 플레이어 중심 임시 카메라 (물류 규칙은 M2A로 대체, 카메라 기준 유지)

- 날짜: 2026-08-06
- 문제: 자동 반경 연결 방식의 생산 루프를 플레이어가 재료를 직접 운반하는 흐름으로 바꾸고, 운반 중 카메라 흔들림을 제거할 것인가?
- 선택지:
  1. 설비 주변의 재료를 자동 흡수·제출하고 플레이어와 대상을 공동 프레이밍한다.
  2. 플레이어가 재료 하나를 집어 호환 설비와 제출대에 명시적으로 넣고, 주변 대상과 공동 프레이밍하지 않는다.
  3. 직접 운반과 카메라 변경을 다음 단계로 미룬다.
- 결정: 당시에는 플레이어가 `밀 집기 → 분쇄 투입 → 밀가루 집기 → 가열 투입 → 빵 집기 → 제출`을 E/Space로 직접 수행하고, 고정 설비가 자동 흡수·제출하지 않도록 했다. 이 기록의 물류 규칙은 아래 M2A 하이브리드 결정으로 대체한다. 현재 임시 카메라는 플레이어만 화면 중심으로 즉시 추적하고, 대상 변화에 따라 중심과 배율을 바꾸지 않는다. 카메라 기준은 유지하며 최종 카메라 방식은 확정하지 않는다.
- 근거: 직접 운반이 병목과 위치 판단을 실제 플레이어 행동으로 만들고, 플레이어 중심 고정 추적이 재료·설비 변화에 따른 화면 흔들림을 줄인다. 최종 시점 후보는 아직 충분한 생산·플레이테스트 증거가 없어 결정하지 않는다.
- 검증 방법: 순수 상태 테스트에서 한 재료 운반·호환성·10개 용량·수동 제출·결정론을 검증하고, 브라우저에서 밀부터 빵 3개 제출까지 E/Space만으로 완료한다. 카메라 테스트에서는 플레이어 위치가 바뀌어도 임시 화면 중심과 배율이 일정한지 확인한다.
- 재검토 조건: 직접 운반이 재료 가독성이나 투입 정확도를 해치거나, 세 카메라 후보 비교 플레이테스트에서 다른 방식이 일관되게 우수하다는 증거가 축적될 때

## 2026-08-06 — 로드맵 상태 분류와 문서 라우팅

- 날짜: 2026-08-06
- 문제: 자동 테스트·빌드 통과, 과거 리뷰 증거, 사람 플레이 기록 부재가 섞여 단계 완료 상태가 실제 검증 수준보다 높게 표시될 수 있다.
- 선택지:
  1. 자동 테스트 또는 빌드 통과를 단계 완료로 취급한다.
  2. 리뷰 로그의 발견 사항만으로 현재 코드 상태를 결정한다.
  3. 코드 구현, 자동 검증, 사람 플레이, 제출 동결을 네 상태로 분리하고 문서 간 라우팅 규칙을 둔다.

- 문제: 같은 종류 출력 토큰과 설비·제출대가 같은 반경에 있을 때 화면의 상호작용 대상과 E 결과가 달라지거나, 비관찰·가득 찬 대상이 다른 토큰의 의도를 가로챌 수 있었다.

  2. 표현 계층의 링만 조정하고 상태 선택 규칙은 유지한다.
  3. authoritative 선택기가 관찰 상태·재료 종류·stack 여유·실제 전달 가능 용량을 함께 판정한다.

- 각 Module이 효과 scalar와 표현 snapshot을 함께 소유한다. 전환은 root, parent, location, socket seat/quaternion을 바꾸지 않으며, 실패 취소는 시작 scalar와 불투명 표현 상태를 정확히 복구한다. 아직 소개되지 않은 모듈과 Again은 이 전환을 소비하지 않는다.

## 2026-08-30 - 바닥 모듈과 이동 블록의 footprint 권위

- `CampaignConfig.interaction.floorModuleHalfExtentMeters = 0.34`가 바닥 Module의 착지·등장 배치와 이동 ProductionBlock sweep이 함께 소비하는 유일한 정사각 footprint half-extent이다. 같은 값인 `moduleSurfaceRadiusMeters`는 E 상호작용 표면 거리라는 별도 의미를 유지한다.
- `location.kind === 'world'`인 Fast/Double/Again만 블록 전용 장애물이다. 이 경계는 블록과 접촉 플레이어에게 적용되는 공통 X 이동량을 제한하지만, 일반 플레이어 충돌에는 Module을 추가하지 않는다. held/not-introduced 및 socket Module은 독립 장애물이 아니며, socket Module은 소유 ProductionBlock footprint를 따른다.

## 2026-08-30 - Stage0 제출대 목표 공개 권위

- Stage0의 실제 bread output 사건은 SubmissionDock이 소유한 한 번의 공개 연출을 시작한다. 제출대의 보이는 V006 모델은 저작 terminal의 `0.62`배에서 `0.50s` cubic ease-out으로 `1`배가 되고, 기존 physical goal board 한 개는 같은 진행률로 저작 Y보다 `0.65m` 아래에서 terminal까지 상승한다.
- authoritative SubmissionDock root, 충돌·흡수·빵 접촉·suction anchor와 목표 수량은 terminal에 고정된다. 공개 전과 진행 중에는 bread intake를 닫고, 완료 또는 취소 시 같은 시각 root와 goal board를 terminal visible/interactable 상태로 만든다. Stage1–3 configure는 별도 연출 없이 즉시 terminal 상태를 사용한다.

## 2026-08-30 - U자 맵 벽 모서리 표현 권위

- `CampaignMap`의 보이는 북쪽 벽이 북서·북동 외곽 모서리 사각을 완전히 소유한다. 북쪽 벽은 playable X bounds에서 양쪽으로 벽 두께 `.34m`만큼 연장되고, 서·동쪽 벽은 playable north face `Z=-3.6`에서 시작해 면 하나만 공유한다. 벽끼리 양의 부피로 겹치거나 틈을 남기지 않는다.
- playable `CAMPAIGN_MAP_BOUNDS`, 모든 anchor, collision, floor, light와 camera는 변경하지 않는다. 이 결정은 constructor-time wall presentation geometry에만 적용한다.

## 2026-08-30 - Stage0 밀 파이프 공개 연출 권위

- Stage0의 실제 달리기 튜토리얼 완료 사건은 WheatSource가 소유한 한 번의 파이프 공개 연출을 시작한다. 역사적으로 승인된 프로필인 `0.42s` cubic ease-out `e = 1 - (1 - p)^3`과 scale `0.92 + 0.08e`를 `CampaignConfig.presentation`의 단일 값으로 사용한다.
- WheatSource의 authoritative root, 벽 부착·밀 생성·배출 anchor와 충돌 경계는 저작 terminal에 고정한다. 같은 root 아래의 보이는 V014 묶음만 presentation wrapper에서 scale을 소비하며, 시작과 동시에 `revealed=true`가 되어 그 프레임부터 기존 1.5초 생성 clock이 진행한다. 취소·실패는 같은 시각 묶음을 scale 1의 visible terminal로 복구하고 Stage1–3은 즉시 terminal 상태를 사용한다.

## 2026-08-30 - 시간제 스테이지 전광판 입장 권위

- Stage1·2·3의 첫 시작과 같은 스테이지 재시도는 `CampaignConfig.presentation.timedStageEntranceSeconds = 0.28`을 소비한다. 기존 중앙 physical scoreboard 한 개가 authoritative 시작 시간 `00:50 / 01:00 / 01:30`을 한 번 그린 뒤 기존 wall-hidden Y에서 active Y까지 smoothstep으로 상승하며, 그 terminal만 `playing`과 countdown을 승인한다.
- 스테이지 데이터 준비, 중앙판 상승, `playing` 게시는 같은 `PresentationPlayer` transaction 안에서 순서대로 실행한다. 상승 프레임은 입력·재료·생산·WheatSource·Module clock·remainingSeconds를 진행하지 않고, terminal을 만든 delta도 gameplay에 재사용하지 않는다. 재시도는 기존 suction→안전 pose→camera return→dock/module reset 순서를 유지한 뒤 같은 입장 step을 소비하며, 취소·fault는 중앙판을 숨기고 기존 재시도 snapshot 또는 이전 스테이지 구성을 복구한다. Stage0와 ordinary 초 단위 digit redraw는 이 입장 연출을 소비하지 않는다.
