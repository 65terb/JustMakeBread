# 실행 계획

이 문서는 [ROADMAP.md](./ROADMAP.md)의 일정과 마일스톤을 저장소 구현 순서로 번역한다. B+ family 방향은 사용자 피드백으로 채택됐지만 최종 projection·shallow Z 폭·block visual scale은 사람 tuning gate로 남아 있다. 최신 순서는 `M3-V0 B+ 내부 tuning → M3-V0.5 Stage 0 lifecycle → M3-V1 [빠르게!] → M3-V2 [두 배로!]`다. `legacy-a`는 사용자-facing 후보가 아닌 명시적 내부 rollback이다. Fast와 Double은 모두 대회 최소 범위이며, 각 앞 단계의 사람 승인 전에는 다음 단계를 시작하지 않는다. 각 단계의 자동 검증과 사람 플레이 검증은 별도로 기록하며, 자동 검증만으로 사람 플레이 완료를 선언하지 않는다.

## 상태 표기

- `미착수`: 현재 저장소에 기능이나 산출물이 없다.
- `구현됨·미검증`: 코드·테스트·문서 산출물은 있으나 사람 플레이 기록이 없다.
- `사람 플레이 검증 완료`: 실제 사람이 재현 가능한 흐름을 플레이하고 `PLAYTEST_LOG.md`에 기록했다.
- `동결`: 제출 후보 이후 신규 기능을 금지하고 치명적 버그만 다룬다.

일정과 범위의 권위는 [ROADMAP.md](./ROADMAP.md)를 따른다. 이 문서가 과거 초안과 충돌하면 `DECISIONS.md`와 `GAME_DESIGN_TRACK1.md`의 최신 결정을 우선한다.

## 단계 0 — M0 기준선 감사와 문서 동기화 (구현됨·미검증)

산출물:

- 대회 사실·가정·미확인 사항의 분리
- 현재 게임 디자인과 폐기된 범위의 분리
- 결정·협업·리뷰·플레이테스트·에셋 기록
- Vite + TypeScript + Three.js 정적 프로젝트 골격
- 실제 코드와 문서의 완료 상태 대조

컷오프:

- 공식 사실과 내부 전략이 같은 문단에서 섞이지 않아야 한다.
- 구현 범위 밖 기능을 이 단계에서 끌어오지 않는다.
- 기능 상태와 자동·사람 검증 상태를 구분한다.

## 단계 1 — M1 조작 기반 (구현됨·미검증)

구현 순서:

1. 플레이어와 상호작용 대상을 안정적으로 보여주는 플레이어 중심 임시 프로토타입 카메라와 단순 바닥
2. 카메라 방식을 교체 가능한 구조로 유지
3. 카메라 때문에 플레이어, 재료 또는 상호작용 대상이 화면 밖으로 사라지지 않게 함
4. 플레이어 프리미티브와 WASD 이동
5. Stage 1 P0의 고정 큐브형 생산 설비 프리미티브와 `분쇄`·`굽기` 월드 명칭
6. 재료·설비·제출대 근접 상호작용 표시
7. E로 재료 하나를 집고 호환 설비·제출대에 직접 투입
8. Stage 1 공개 상태에 따라 파이프·`분쇄`·`굽기`·제출대를 사건 순서로 표시
9. 같은 종류 재료 1~5개 stack 운반·bulk 투입과 생산 블록 상태의 상호배제
10. 맵 네 방향 경계벽과 넓은 이동 공간
11. 순수 게임 로직의 이동·집기·호환성·공개 lifecycle 테스트

컷오프:

- 새로고침 후 브라우저 입력이 시작되지 않으면 다음 단계로 가지 않는다.
- 서로 다른 재료가 섞이거나 5개를 초과해 들 수 있거나, 재료가 잘못된 설비로 들어가면 다음 단계로 가지 않는다.
- 이동 중 플레이어와 현재 상호작용 대상이 지속적으로 식별되어야 한다.
- 카메라 때문에 이동 방향, 재료 투입 위치 또는 거리 판단이 불명확하면 다음 단계로 넘어가지 않는다.
- 현재 임시 카메라가 플레이를 방해한다면 최종 아트 작업 전에 교체한다.
- `npm.cmd run check` 또는 `npm.cmd run build`가 실패하면 기능을 추가하지 않고 먼저 고친다.

Stage 1 P0에서는 공개된 `분쇄`·`굽기` 설비를 고정하고 Space 집기를 거부한다. 기존 M2A 이동·스냅 코드는 내부 호환 경로로 보존하지만 현재 활성 공개 흐름에 포함하지 않는다.

## 단계 2 — M2/M2A 최소 생산 수직 슬라이스 (구현됨·미검증)

현재 활성 Stage 1 P0는 이동 가능한 생산 블록과 직접 운반을 사용한다. 플레이어 전용 시작 상태에서 파이프를 1.0초에 공개하고, 이후 밀 생성·설비·제출대를 원인 사건에 따라 순차 공개한다. 초기 설비 위치는 서로 분리되어 무입력으로 전체 사슬이 연결되지 않는다. 상태 모델의 자동 흡수·자동 제출은 내부 호환 경로로 보존하되, 공개된 `분쇄`·`굽기`는 Space로 들어 다시 놓을 수 있고 Stage 1의 기본 재료 조작은 E 직접 운반이다. 현재 속도 기준은 밀 생성 `4.0초`, 분쇄·굽기 처리 `3.2초`이며, 자동 흡수 `0.12초`, 관찰 지연 `0.25초`, 기본 버퍼 `5개`, 활성 밀 `10개`, 출력 표현 애니메이션 `360ms`는 유지한다. 명시적 `productionCapacity` fixture override는 별도로 허용하며, 처리속도·목표·점수는 이 버퍼 변경으로 바꾸지 않는다. 재료는 같은 종류만 1~5개까지 stack할 수 있고, 호환 설비·제출대에는 여유만큼 bulk 전달한 뒤 잔량을 계속 든다. 밀 생성 표현은 서쪽 벽 고정부에서 실내 +X 방향으로 곧게 나온 수평 파이프의 정면 mouth 앞에서 시작해 약 0.55초 동안 forward burst와 하강 궤적으로 authoritative 바닥 위치에 수렴하는 시각 동작이며 상태 시간을 바꾸지 않는다. 첫 빵 출력 뒤에는 두 줄 최소 목표 HUD를 표시하고 그 전에는 숨긴다.

구현 순서:

1. 밀 → 분쇄 → 밀가루 → 굽기 → 빵 → 제출대의 순수 상태 수직 슬라이스와 같은 종류 stack 물류
2. `wheat`, `flour`, `bread` 실제 월드 토큰과 결정론적 생성·출력 위치
3. 밀 생성원의 활성 토큰 상한과 관찰 지연
4. visible 밀 pickup 직후 고정 `분쇄` 공개와 E 직접 투입
5. 분쇄 처리 후 밀가루 output과 고정 `굽기` 공개
6. 굽기 처리 후 빵 output과 제출대 공개
7. 관찰 지연과 실제 월드 출력 위치를 유지한 1~5개 token stack 운반
8. 공개된 제출대의 Stage 0 첫 주문 빵 1개 목표와 자동 클리어 금지
9. 상태 모델의 호환성·예약·버퍼·자동 흡수·자동 제출과 bulk 수동 전달 규칙 회귀
10. 긴 상시 조작 HUD 없이 설비·토큰·처리 상태·출력 위치를 월드 라벨·출력·상호작용 링으로 읽고, 첫 빵 출력 뒤에만 `빵을 제출하세요`와 제출 수량을 표시하며, 실패·완료일 때 최소 결과 피드백을 표시하는 가독성
11. 포인터·포커스·문서·페이지 이벤트 뒤 WASD 이동 상태의 취소와 새 입력 재개
12. 서쪽 벽 고정부에서 실내 +X로 곧게 나온 밀 생성 직관 파이프와 정면 mouth·전방 burst/하강 궤적, 카메라에서 읽히는 북쪽 벽 수납형 제출대, 큐브 면 설비 명칭, 얕은 중립 출력 포켓과 결정론적 토큰 적체
13. 실제 이동 거리 기반 플레이어 유휴·걷기·운반 모션과 이동 정면 동기화
14. 바닥에서 약 1.12 높이의 수평 밀 생성 mouth, mouth 앞의 짧은 +X burst와 authoritative 바닥 적체까지 약 0.55초의 표현 전용 하강 궤적, 3.2초 처리 진행을 읽히게 하는 링·발광·출구 신호
15. 고정 `분쇄`·`굽기`와 북쪽 벽 제출대의 600ms 비차단 one-shot 공개 정착, 고정 설비·벽 고정부와 분리된 local motion, reduced-motion 즉시 최종 상태

현재 자동 검증 범위:

- 밀 생성이 `4.0초` 전에는 일어나지 않고 정확히 `4.0초`에 발생하며, `40초`에 활성 밀 10개 상한에 도달하는지 검증한다.
- 분쇄·굽기가 동일하게 `3.2초` 전에는 출력하지 않고 정확히 `3.2초`에 출력하는지 검증한다.
- 생성 간격·생성 상한·호환성·예약 중복 방지·순차 흡수·처리·출력·제출·수동 보완·큰 프레임 결정론을 순수 TypeScript 테스트로 검증한다.
- 밀 출현 표현 helper는 출구 높이에서 시작해 약 `0.55초`에 바닥으로 수렴하고 음수 높이가 없으며 완료 후 안정적인지 별도 순수 테스트로 검증한다. 이 표현은 authoritative 생성 위치·관찰 지연·집기 가능 시점을 변경하지 않는다.
- 설비·제출대 공개 표현 helper는 600ms 이전의 bounded offset·scale·contact cue와 450ms 이후 안정, 600ms 이후 final, variant별 벽면 부착·reduced-motion·one-shot controller를 순수 테스트로 검증한다. 표현은 입력·공개 trigger·HUD·상호작용을 지연하지 않는다.
- 자동 테스트와 프로덕션 빌드는 코드 구현 증거이며 사람 플레이 승인으로 승격하지 않는다.

완료 컷오프 (현재 미충족):

- 새로고침 후 7~10초 무입력 상태에서 완료되지 않고, 밀 토큰이 생성원 주변에 실제로 누적되어야 한다.
- 초기 상태에서 세 구간이 자동 연결되지 않아야 하며, 플레이어가 재료를 직접 운반해 각 공개 설비에 투입해야 한다.
- 생성·출력 토큰이 같은 시뮬레이션 스텝에 바로 흡수·제출되지 않고, 월드에서 관찰 가능해야 한다.
- 분쇄는 밀만, 굽기는 밀가루만 받으며 기본 내부 저장량과 예약량의 합이 5개를 넘지 않아야 한다. 명시적 fixture 용량 override가 있는 테스트는 해당 값을 따른다.
- 플레이어가 직접 운반과 Space 생산 블록 재배치로 생산 사슬을 연결하고 첫 주문 빵 1개를 제출하는 전체 흐름을 사람 플레이로 확인해야 한다. 후속 주문의 더 큰 target은 별도 lifecycle 범위다.
- 같은 종류 재료 1~5개가 E 한 번마다 안정적인 순서로 쌓이고, 설비·제출대의 여유만큼 bulk 전달되며 잔량·혼합 거부가 읽혀야 한다.
- 토큰 적체, 설비 라벨, 흡수 범위, 출력 위치, 현재 운반물이 화면에서 읽혀야 한다. 첫 빵 출력 순간에는 목표 HUD가 정확히 `빵을 제출하세요` / `0 / 1`으로 시작하고 제출에 따라 갱신되어야 한다.
- 수정 전 사용자 플레이에서 전체 생산·제출은 성공했지만 입력 고착과 생산 출구·토큰 가독성 문제가 발견되었으므로, 수정 후 동일 흐름과 취소 입력을 다시 확인해야 한다.
- 밀 생성 파이프가 서쪽 벽에 고정되어 실내로 돌출되어 보이고, 카메라에서 읽히는 북쪽 벽 수납형 제출대의 밝은 라벨·세로 투입구와 선반, 분쇄·굽기 큐브의 면 글자와 얕은 중립 출력 포켓 아래 최소 5개 적체가 읽혀야 한다. 운반 중에는 두 팔과 손이 재료를 가슴 앞에서 함께 받쳐야 한다.
- 실제 이동 거리가 0인 벽 밀착 상태에서는 걷기 모션이 진행되지 않고, 이동 정면과 운반물의 위치가 동기화되어야 한다.
- 포인터 누름·창 포커스 이탈·탭 전환·페이지 이탈 뒤에는 이동이 0이어야 하며, 새 non-repeat WASD 입력 전 repeat keydown만으로 재개되지 않아야 한다.
- 이동 중 플레이어 중심과 임시 카메라 배율이 대상 변화에 따라 흔들리지 않아야 한다.
- 밀 생성원의 벽 고정부→수평 직관→정면 mouth 축이 보이고, 첫 밀과 후속 밀은 같은 mouth 앞에서 +X로 짧게 방출된 뒤 바닥 적체로 하강해야 한다. 파이프·토큰·바닥이 교차하지 않아야 하며, 분쇄·굽기 처리의 3.2초 진행 신호가 유휴 상태와 구분되어야 한다.
- `PLAYTEST_LOG.md`에 실제 사람의 무입력 미완료·블록 배치·첫 자동 흡수·첫 빵·첫 주문 1개 제출 결과를 기록해야 한다. 이후 더 큰 주문 목표는 별도 주문 설정과 사람 검증으로 기록한다.
- 공개 배포 URL에서 직접 접근·새로고침·입력 시작을 확인해야 한다.

현재 상태: Stage 1 P0 공개 lifecycle과 코드 기반 표현은 자동 테스트·빌드·구현자 브라우저 확인 기준으로 `구현됨·미검증`이다. `PLAYTEST_LOG.md`의 수정 전 사용자 플레이 성공은 보존하되, 새 사람 플레이와 공개 배포 확인 전에는 Stage 1 또는 단계 2를 최종 완료로 표시하지 않는다.

## 단계 3 — M3-V0/V1/V2 방향·수식 블록 게이트 (V0 구현됨·사람 비교 미검증)

### M3-V0 공간·가독성

구현 순서:

1. 현재 Stage 1 규칙을 그대로 사용하는 압축 생산선 layout helper
2. 같은 layout에서 약 15~25% closer framing 후보인 직교·낮은 FOV 원근 카메라 비교
3. X축 중심 이동과 얕은 자유 Z 범위
4. `밀 생성 → 집기 → 분쇄 → 밀가루 출력·적체`까지만 연결

현재 구현 상태: 한 빌드에서 `?view=bplus-ortho`, `?view=bplus-balanced`, `?view=bplus-perspective`를 선택한다. query의 첫 값이 모드를 소유하며 기본값·잘못된 첫 값은 `bplus-balanced`로 fail-closed 복귀한다. `view=legacy-a`는 명시적 deprecated/internal rollback이다. `?compare=views`에서만 B+ 세 버튼 비교 패널을 표시하고, 버튼 선택은 query/hash를 보존한 full reload로 같은 초기 GameState/lifecycle을 다시 시작한다. 일반 플레이 URL에는 패널이 없으며 패널 포커스·포인터 입력은 movement reset과 조화된다. 세 B+ 후보는 M1-derived X `[-12.35, 12.35]` / width `24.7`, Z `[-3.6, 3.6]` / depth `7.2` layout과 자유 Z를 `GameState`·충돌·상호작용·렌더에 함께 사용한다. 모든 authoritative token slot 기준 각 생산 구간의 collision-free 이동 하한은 약 `0.56초`다. 18% closer framing, X축 dead-zone·부드러운 추적·clamp, Z 비반응을 공유하고, 들고 있는 생산 블록은 북쪽 벽에 붙은 설비의 보이지 않는 X-only 제약과 외곽까지 벽 안에 남아야 하며 invalid continuous-X/contact/collision drop에서는 held 상태를 유지한다. 화면 레일 표현은 없다. balanced는 FOV `21`·거리 배율 `1.2`의 실제 PerspectiveCamera다. 자동 테스트는 완료했지만 최종 projection·Z 폭·블록 visual scale·front/side 이동 체감은 사람 tuning lane이다.
